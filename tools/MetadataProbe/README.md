# Исследование источников метаданных Qadam

Дата: 7 ноября 2026. Отдельный прототип на .NET 8, не подключённый к интерфейсу Qadam. Он читает список объектов из `ConfigDumpInfo.xml` и сравнивает два списка. Никаких кликов, запуска 1С, подключения к базе, сетевых запросов или изменения исходных XML программа не выполняет.

## Вывод для архитектуры

Нужно разделить три состояния: сохранённая основная конфигурация, применённая конфигурация БД и несохранённые изменения открытого редактора. Они не взаимозаменяемы. Для конфигурации, расширения и каждого документа нужны отдельные идентификаторы и признаки актуальности.

| Источник | Что даёт | Ограничение |
|---|---|---|
| Нынешний MXL в Qadam | Имена и часть свойств метаданных | Управляет окнами и мышью; не содержит тексты модулей |
| ConfigDumpInfo штатного Конфигуратора | Имена, ID, версии объектов и внешних свойств | Не содержит полные свойства, сигнатуры и тексты; сам файл не доказывает, когда и из какой базы его выгрузили |
| Иерархическая XML/BSL-выгрузка | Детальные метаданные, тексты модулей, основа для индекса | Первая выгрузка может быть большой; обновление требует контроля завершения и блокировок |
| Внешнее соединение или приложение ИР | Метаданные доступной приложению конфигурации | Нельзя считать снимком несохранённых изменений обычного Конфигуратора |
| UIA текущего документа | Текущий текст/выделение, включая ввод пользователя | Не является источником всей конфигурации; нужна проверка идентичности документа |
| Внутренний адаптер по принципу Снегопата | Исторически существовал доступ к редактируемому контейнеру и текстам модулей | Для 8.3.26/8.3.27 современный ABI и стабильность ещё не подтверждены |

Предлагаемый маршрут: отдельный процесс получения сохранённых метаданных → небольшой реестр версий → выборочное обновление XML/модулей → локальный индекс → интерфейс Qadam. Текущий несохранённый модуль накладывается поверх сохранённого индекса, а не подменяет всю конфигурацию. Экспериментальный внутренний адаптер должен подключаться к тому же контракту источника; UI не должен зависеть от его успеха.

`ConfigDumpInfo` — кандидат для определения изменений, а не обещание мгновенного индексирования. Скорость, блокировки второго Конфигуратора и доступ к сохранённой основной конфигурации при открытом редакторе требуют живой проверки. Ошибка получения нового снимка должна оставлять прежний индекс доступным с пометкой о его возрасте.

Полное переписывание приложения пока не обосновано. Сначала проверяется отдельный источник данных; существующие подсказки и навигация могут использовать новое ядро через адаптер.

Для сравнения на тестовой базе нужны три варианта: текущий MXL, получение реестра версий с дальнейшей XML-выгрузкой и копирование выбранных объектов через специальные форматы буфера. Последний вариант всё ещё взаимодействует с интерфейсом и временно меняет буфер; его нельзя называть фоновым API. Измерять следует время первого/повторного получения, воздействие на фокус и clipboard, доступность новых несохранённых объектов, полноту модулей и поведение отмены. Прямой внутренний адаптер исследуется отдельно, без переноса адресов старых сборок.

## Штатные механизмы 1С

В руководстве 8.3.27 описан `/DumpConfigToFiles <каталог> -configDumpInfoOnly`: выгружается только файл версий. Этот флаг можно сочетать только с `-Format`, а не с `-update` или `-getChanges`.

Для детальной выгрузки отдельно предусмотрены `-update`, `-getChanges`, `-listFile` и работа с расширениями. Их совместимость нужно соблюдать по документации; они не должны автоматически добавляться все вместе.

Режим `/AgentMode` запускает специальный Конфигуратор с SSH/SFTP-интерфейсом. Это не обнаруженный API подключения к уже открытому обычному Конфигуратору. Поэтому такой режим сам по себе не решает получение несохранённых правок.

Ещё один кандидат для предварительной проверки — `/GetConfigGenerationID`: возвращает идентификатор поколения, сравниваемый только на равенство. Если его получение окажется достаточно дешёвым и доступным одновременно с редактором, при неизменном поколении можно не выгружать реестр. Это проектная гипотеза, не выполненный замер.

Источник: [руководство администратора 1С 8.3.27, разделы 7.4.4 и 4.7](https://1c-dn.com/library/tutorials/1c_enterprise_administrator_guide_file_mode_8_3_27/).

## TurboConf и прямой доступ

Официальная [справка TurboConf](https://turboconf.ru/TurboConf/Help) описывает сохраняемый кэш конфигурации и расширений. В [задаче 10736](https://turboconf.ru/Tasks/Details/10736) разработчик обсуждает время формирования отчёта по конфигурации и проблемы UIA при перечислении расширений. Это свидетельствует об использовании интерфейсного пути, но не раскрывает весь внутренний алгоритм.

[ИР-адаптер](https://fastcode.im/Templates/8474/ir-avtodopolnenie--kontekstnaya-podskazka) отдельно использует приложение ИР, кэши модулей и форм. Нельзя приписывать его архитектуру базовому TurboConf.

В [исходнике Снегопата](https://github.com/infostart-hub/snegopat_modul/blob/master/engine/com_metadata.as) `editedMetaDataCont()` получает контейнер через службу редактирования, а `getIBMDCont()` использует другой путь. `getModuleText()` обращается к помощнику редактора модулей. Это подтверждает существование такого подхода в старой реализации. [Репозиторий](https://github.com/infostart-hub/snegopat_modul) помечен неподдерживаемым, x64 проверялся на 8.3.18. Чужой код в прототип не переносился.

## Запуск прототипа

Из корня Qadam:

```powershell
dotnet run --project tools/MetadataProbe -- self-test
dotnet run --project tools/MetadataProbe -- inspect '<путь к ConfigDumpInfo.xml>' '<постоянный ID базы>'
dotnet run --project tools/MetadataProbe -- compare '<старый ConfigDumpInfo.xml>' '<новый ConfigDumpInfo.xml>' '<ID базы>'
```

Для `compare` вызывающая сторона обязана подтвердить, что оба файла получены из одной базы: имя базы не хранится в стандартном XML. Программа дополнительно сверяет ID конфигурации и формат. Для одинаковых копий конфигурации в разных базах UUID конфигурации недостаточен.

Результат — JSON в stdout. Имена объектов могут быть клиентскими данными: вывод хранится локально и не предназначен для отправки во внешние сервисы.

## Проверки и границы

Сборка на .NET SDK 8.0.427 успешна. Пройдены 13 синтетических проверок: вложенные объекты, кириллица, неизменённый снимок, переименование по ID, изменение версии, добавление/удаление, разделение баз/расширений, смена формата, дубликаты, неполный и оборванный XML, неизвестное пространство имён, запрет внешних XML-сущностей.

Изменение версии объекта не означает доказанного изменения конкретного свойства. Вложенные записи без собственной версии могут требовать обновления родителя. Сравнение реестров не заменяет смысловой diff XML и BSL.

Пока не проверены: настоящий `ConfigDumpInfo.xml` из локальной платформы, скорость большой конфигурации, серверные базы, расширения и одновременная работа с открытым Конфигуратором. Рабочие базы не использовались.
